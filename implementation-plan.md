# Implementation Plan — EPMCDMETST-59266

## Jira User Story
- **Key**: EPMCDMETST-59266
- **Title**: Enforce unique Employee ID and add user-friendly form validation
- **Acceptance Criteria**
  1) The system prevents saving an employee with an `emp_id` that already exists.
  2) On validation failure, the form is re-rendered with clear messages and previously entered values retained (where safe).

---

## 1) Objective
Implement **server-side validation** for Employee create/update flows and enforce **uniqueness of `Emp.emp_id`** so that duplicate employee IDs cannot be saved. When validation fails, re-render the form with **clear error messages** and **retain user input**.

## 2) Scope
- Add a **uniqueness constraint** for `Emp.emp_id` at the database/model level.
- Introduce a Django **ModelForm** (or Form) for `Emp` that provides:
  - required-field validation for existing form fields (at minimum `emp_id`, plus any other field currently required by the model)
  - uniqueness validation for `emp_id` with a user-friendly message
- Update `add_emp` and `do_update_emp` views to use the form:
  - on success: save and redirect to `/emp/home/`
  - on failure: re-render the relevant template with errors and pre-filled values
- Update templates (`add_emp.html`, `update_emp.html`) to:
  - display field-specific validation errors
  - keep previously entered values on errors

## 3) Out of scope
- UI/UX redesign beyond adding error rendering.
- Changing field types/lengths (e.g., phone from `CharField` to numeric) unless required to satisfy the acceptance criteria.
- Adding client-side validation; server-side validation is the source of truth.
- Refactoring unrelated features (search, delete semantics, navbar, home dashboard).

## 4) Existing components
- Django app: `emp`
- Model: `emp/models.py` defines `Emp` with `emp_id = models.CharField(max_length=200)` (currently not unique)
- Views: `emp/views.py`
  - `add_emp` reads from `request.POST` and saves directly
  - `do_update_emp` updates an existing instance and saves directly
- Templates:
  - `templates/emp/add_emp.html`
  - `templates/emp/update_emp.html`
- Current forms are plain HTML; no Django forms used.

## 5) Impacted files
### New files
- `emp/forms.py` (new): `EmpForm` ModelForm with validation.

### Modified files
- `emp/models.py`: mark `emp_id` as `unique=True` (and/or add `UniqueConstraint`).
- `emp/views.py`: replace manual POST parsing with form-based validation and error handling.
- `templates/emp/add_emp.html`: show errors and preserve values.
- `templates/emp/update_emp.html`: show errors and preserve values.
- `emp/migrations/XXXX_*.py`: new migration generated by `makemigrations` for uniqueness constraint.
- `emp/tests.py`: add/extend tests for uniqueness + validation UX expectations.

## 6) Frontend changes
- In `add_emp.html` and `update_emp.html`:
  - Render errors near each field (Bootstrap-friendly), e.g.
    - `{{ form.emp_id.errors }}` displayed under Employee ID
  - Bind input values to `form` so failed submissions re-populate fields.
  - Checkbox `working`: ensure it reflects bound value when form is invalid.

## 7) Backend changes
### 7.1 Model / DB constraint
- Update `Emp.emp_id` to be unique:
  - Preferred: `emp_id = models.CharField(max_length=200, unique=True)`.
  - Alternative: `Meta.constraints = [UniqueConstraint(fields=['emp_id'], ...)]`.
- Generate migration and ensure it applies cleanly.
- Consider existing data: if duplicates already exist, migration may fail; plan includes a pre-migration check.

### 7.2 Form layer
- Add `EmpForm(forms.ModelForm)`:
  - Map form fields to `Emp` fields.
  - Add `clean_emp_id` to raise `ValidationError("Employee ID already exists")` on duplicates.
  - For update flow, exclude current instance from uniqueness check.

### 7.3 Views
- `add_emp`:
  - GET: instantiate empty `EmpForm()` and render.
  - POST: bind `EmpForm(request.POST)`; if valid save; else render template with `form`.
- `do_update_emp`:
  - Keep route structure (don’t change URLs).
  - POST: fetch instance, bind `EmpForm(request.POST, instance=e)`; validate; save; else render `update_emp.html` with bound `form`.

## 8) Database impact
- **Schema change**: add unique constraint/index on `emp.emp_id`.
- Migration risk if existing `db.sqlite3` has duplicate `emp_id` values.

## 9) Testing strategy
### Automated (Django TestCase)
Add tests in `emp/tests.py`:
1. Duplicate `emp_id` on create is rejected (no new row; error shown).
2. Updating an employee to a conflicting `emp_id` is rejected.
3. Updating an employee without changing `emp_id` succeeds.
4. On failure, response HTML retains submitted values (at least `emp_id` and `name`).

### Manual
- Add employee normally → redirect to home.
- Add duplicate `emp_id` → inline error + retained input.
- Update to duplicate `emp_id` → inline error + retained edits.

## 10) Risks
- Migration may fail due to existing duplicates.
- Template binding changes could accidentally drop current styling/labels if not handled carefully.

## 11) Assumptions
- SQLite is the primary dev DB.
- Introducing Django forms is acceptable for validation.
- Case-sensitive uniqueness is acceptable (not specified otherwise).

## 12) Implementation sequence (dependency-ordered)
1. Check for duplicate `emp_id` in current DB.
2. Add unique constraint in `emp/models.py`.
3. Generate/apply migration.
4. Create `emp/forms.py` with `EmpForm` and `clean_emp_id`.
5. Refactor `emp/views.py` add/update to use the form and re-render on errors.
6. Update templates to display errors and bind values to `form`.
7. Add/adjust tests.
8. Run migrations + unit tests + smoke test.

---

## Traceability (AC → implementation)
- **AC1**: DB unique constraint + form `clean_emp_id` + save only when valid + tests.
- **AC2**: Return bound form with errors to template + template renders errors and uses bound values + tests.
